# Project FORESIGHT — AI-Powered Demand & Inventory Intelligence

Zidio Development · Data Science & Analytics Internship · Client engagement: **NorthBay Living**
(a simulated D2C home & lifestyle brand, per `Zidio_Project_Data_1.1.pdf`)

## The problem

NorthBay Living plans inventory for ~200 SKUs on gut feel and spreadsheets. They lose money in
two directions at once: best-sellers stock out (lost sales) and slow movers pile up (cash locked
in stock that eventually gets marked down). FORESIGHT turns their sales, inventory, and calendar
data into a weekly SKU-level demand forecast and a stockout/overstock early-warning system the
operations team can act on without a data scientist in the room.

## About the data

**The engagement brief references a synthetic dataset "that accompanies this brief," but only the
brief PDF was provided in this session — no raw CSVs or generator script.** Per the brief's own
instruction ("data is provided — generating it is not your job"), `src/generate_data.py` exists
solely to stand in for that missing extract: it produces the four raw tables (`sales_daily`,
`sku_master`, `calendar`, `inventory_snapshots`) matching the schema in Appendix A, with demand and
stock **simulated jointly** (not independently) so the data exhibits the real business problem the
brief describes — chronic stockouts, overstock, and realistic export blemishes (inconsistent
category casing, duplicates, missing values, mixed date formats). It is run once, up front; every
downstream deliverable treats its output as an opaque, imperfect client export and does not import
from it. If real NorthBay extracts ever become available, drop them into `data/raw/` in the same
schema and skip straight to `src/pipeline.py` — nothing downstream changes.

## Setup & run (reproduces everything from raw data with these commands, in order)

```bash
pip3 install -r requirements.txt        # add --break-system-packages if needed

python3 src/generate_data.py            # only if data/raw/ is empty — produces the 4 raw CSVs
python3 src/pipeline.py                 # D1 — clean, join, feature-engineer -> data/processed/master_dataset.parquet
python3 src/forecast.py                 # D3 — backtest + train + forecast -> reports/model_performance.md
python3 src/risk.py                     # D4 — stockout/overstock scoring -> reports/risk_summary.md

# D2 — EDA notebook (rebuild + execute; or just open notebooks/01_eda.ipynb, already executed)
python3 notebooks/build_01_eda.py
jupyter nbconvert --to notebook --execute --inplace notebooks/01_eda.ipynb

# D5 — dashboard
streamlit run app/Home.py

# D6 — scoring API (interactive docs at /docs)
uvicorn service.main:app --reload --port 8000

# Tests (dashboard smoke tests — every page executes without raising)
python3 -m pytest tests/ -v
```

Each script is idempotent and safe to re-run; `src/pipeline.py`, `src/forecast.py`, and `src/risk.py`
must run in that order since each consumes the previous step's output from `data/processed/`.

## Headline backtest result (D3)

Weekly, SKU-level forecast, 6-week horizon, **10-fold walk-forward (rolling-origin) backtest** —
every fold trains only on data available at that fold's origin, so no fold ever sees its own or a
later test window.

| Metric | Model (LightGBM, tweedie objective) | Seasonal-naive baseline |
|---|---|---|
| **WAPE** (primary) | **0.290** | 0.379 |
| MAPE (secondary) | 0.388 | 0.588 |
| Bias (signed) | −1.30 | +0.93 |

**The model beats the baseline by 23.5% (WAPE), on all 10 of 10 backtest folds** — not a one-off.
Per the engagement's non-negotiable rule, we ship whichever wins the honest backtest; full detail
and per-fold numbers are in `reports/model_performance.md`.

## Key assumptions & known limitations

- **The model forecasts recorded sell-through demand, not true unconstrained demand.** The EDA
  (`notebooks/01_eda.ipynb`, §5–6) shows recorded sales are censored by stockouts — when on-hand
  stock hits zero, sales silently understate real demand. Inventory position was **deliberately
  excluded** from the forecasting model's features to avoid teaching it "low stock → low demand,"
  which would produce artificially low forecasts for exactly the SKUs most in need of reordering.
  This is a real limitation: for the ~43 chronically stocked-out SKUs identified in the EDA, true
  demand is likely higher than the forecast shows.
- **Promotions and holidays are assumed knowable in advance** (as a real retailer's promo calendar
  would be) and used as forward-looking features for the forecast horizon — no future *sales* data
  ever leaks into a feature.
- **Newly launched SKUs get low-confidence forecasts**, flagged explicitly in the forecast output
  and dashboard, falling back toward category-level patterns until more history accrues.
- **Rupee figures are planning estimates**, not guaranteed outcomes — they combine current list
  price / unit cost with a lead-time-based stockout probability and a weeks-of-cover overstock rule
  (both fully documented and transparent — see `src/risk.py` and `reports/risk_summary.md`).
- **Scope is fixed on purpose** (per the brief): no live system integration, no price optimisation
  or supplier selection, no automated purchase-order placement. This is a forecast-and-flag tool the
  operations team acts on, not an autonomous one.
- A Power BI dashboard was sketched in supplementary planning notes but is **out of scope for this
  build** — Power BI Desktop is proprietary Windows software that cannot run in this environment.
  The Streamlit dashboard (D5) and FastAPI service (D6) are the actual graded/required deliverables
  and are both fully built and tested.

## Deploying D5 / D6 publicly

This environment cannot expose a persistent public URL. To get one:

- **Dashboard:** push this repo to GitHub and deploy `app/Home.py` on
  [Streamlit Community Cloud](https://streamlit.io/cloud) (free) or Hugging Face Spaces.
- **Scoring service:** deploy `service/main.py` (a standard FastAPI app) on
  [Render](https://render.com), Railway, or Hugging Face Spaces (Docker). Start command:
  `uvicorn service.main:app --host 0.0.0.0 --port $PORT`.

Both were run and fully exercised locally in this environment (dashboard: all 7 pages pass an
automated `AppTest` smoke suite in `tests/`; API: `/health`, `/skus`, `/score/{sku_id}`, and
`/score/batch` all verified, including 404/422 error handling for bad input).
